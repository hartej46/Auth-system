# Generic Plug-and-Play Email Authentication System

A production-ready, modular email-based authentication system built with Express 5, TypeScript, PostgreSQL, Redis, and JSON Web Tokens (JWT).

Designed to be forked, cloned, or imported directly into any backend project with minimal configuration.

---

## Overview

This system provides a complete email-based authentication and session-management backend. It handles user registration with email OTP verification, password-based login, multi-device session tracking, cryptographic CSRF protection, and automatic session token rotation.

---

## How It Works

### 1. Registration Flow and Pre-Registration Staging
- When a user signs up via `POST /api/auth/signup`, the application validates the input using Zod schemas and hashes the password with bcrypt.
- The registration draft (name, email, hashed password, and a 6-digit random OTP) is stored in **Redis** with a 5-minute Time-To-Live (TTL).
- A 60-second cooldown key is also stored in Redis to prevent spamming OTP requests.
- The unverified user is **not** written to PostgreSQL yet. This design prevents database pollution with unverified or abandoned accounts.
- The user receives an email containing the 6-digit verification code.
- When the user calls `POST /api/auth/verify-otp`, the server validates the OTP against Redis. Upon successful validation, the user is written to PostgreSQL inside an atomic transaction, a new session is initialized, and authentication tokens are issued.

### 2. Dual-Token Architecture
The system uses a combination of short-lived and long-lived tokens:
- **Access Token**: A short-lived JWT (default: 15 minutes) signed with `ACCESS_TOKEN_GENERATOR`. It is transmitted by clients in the HTTP `Authorization: Bearer <token>` header. It contains the user ID, session ID, name, and email.
- **Refresh Token**: A long-lived JWT (default: 7 days) signed with `REFRESH_TOKEN_GENERATOR`. It is stored inside an `httpOnly`, `secure`, `sameSite: "lax"` HTTP cookie, making it inaccessible to malicious client-side JavaScript.

### 3. Double-Submit CSRF Protection with HMAC Verification
To prevent Cross-Site Request Forgery (CSRF) on cookie-based refresh operations:
- Every active session created in PostgreSQL stores a cryptographically secure random `csrf_secret` (32 bytes hex).
- The CSRF token is an HMAC-SHA256 signature generated by hashing the Refresh Token with the session's `csrf_secret`.
- The CSRF token is delivered to the browser in a readable cookie (`csrfToken`).
- For state-changing operations or token refreshes, clients send this value back via the `x-csrf-token` HTTP header.
- The server validates that the cookie matches the header using constant-time comparison (`crypto.timingSafeEqual`), verifying that the request came from an authenticated browser origin that can read the cookie.

### 4. Transparent Silent Re-Authentication Middleware
The `authentication` middleware ([src/middlewares/auth.middleware.ts](src/middlewares/auth.middleware.ts)) secures protected routes:
- It first checks and verifies the Bearer Access Token.
- If the Access Token is valid, the user object is attached to `req.user` and execution continues.
- If the Access Token is expired (`TokenExpiredError`), the middleware automatically performs a fallback session verification using the Refresh Token and CSRF tokens without rejecting the client's request.
- If the session is valid and active in PostgreSQL, the middleware:
  1. Rotates the session credentials in the database (updates `last_used_at`, sets a new `csrf_secret`, and extends the expiration).
  2. Generates a fresh Access Token, Refresh Token, and CSRF token.
  3. Attaches the new Access Token to the response in the `x-Access-Token` header.
  4. Sets the updated `refreshToken` and `csrfToken` cookies.
  5. Attaches the loaded user to `req.user` and permits the request to complete.
- This ensures seamless client operation without sudden session drops.

### 5. Multi-Device Session Management and Revocation
- Every login creates a record in the `sessions` table in PostgreSQL, storing IP address, User-Agent, device metadata, creation timestamp, and expiration.
- Users can view their active sessions with `GET /api/auth/sessions`.
- Users can revoke a specific device or remote session with `DELETE /api/auth/sessions/:sessionId`.
- Users can log out of all active devices at once via `POST /api/auth/logout-all`.
- When a user resets their password, all existing active sessions are automatically revoked in the database for security.

### 6. Password Recovery
- `POST /api/auth/forgot-password`: Generates a 6-digit reset OTP and stores it in Redis with a 5-minute expiry. A consistent generic response is returned regardless of whether the email exists, preventing user enumeration.
- `POST /api/auth/reset-password`: Validates the reset OTP from Redis, updates the user password in PostgreSQL, revokes all active sessions, and deletes the temporary Redis key.

## Commands to Run

### Prerequisites
Before running the application, ensure the following are installed:
- Node.js (version 18 or higher)
- PostgreSQL database
- Redis instance
- SMTP server credentials (such as Gmail App Password)

### Step 1: Clone or Navigate to the Directory
```bash
cd "Auth System"
```

### Step 2: Install Dependencies
```bash
npm install
```

### Step 3: Configure Environment Variables
Copy the example environment file:
```bash
cp .env.example .env
```
Open `.env` and fill in your database, Redis, SMTP, and JWT settings:
```env
PORT=8000
NODE_ENV=development
CORS_ORIGIN=http://localhost:3000

# PostgreSQL
CONNECTION_STRING=postgresql://postgres:your_password@localhost:5432/your_database
DB_SSL=false

# Redis
REDIS_HOST=localhost
REDIS_PORT=6379
REDIS_USERNAME=
REDIS_PASSWORD=

# JWT Secrets and Durations
ACCESS_TOKEN_GENERATOR=your_access_token_secret_here
REFRESH_TOKEN_GENERATOR=your_refresh_token_secret_here
ACCESS_TOKEN_EXPIRY=15m
REFRESH_TOKEN_EXPIRY=7d

# SMTP Configuration
SMTP_HOST=smtp.gmail.com
SMTP_PORT=587
SMTP_USER=your_email@gmail.com
SMTP_PASS=your_email_app_password
APP_NAME=Auth System
```

### Step 4: Run the Development Server
```bash
npm run dev
```
The server will start with live-reload using `tsx watch` on `http://localhost:8000`.
On boot, it automatically creates the `users` and `sessions` tables in PostgreSQL if they do not exist.

### Step 5: Run in Production Mode
```bash
npm run start
```

### Other Helpful Commands
- Check TypeScript types:
  ```bash
  npx tsc
  ```
- Format code with Prettier:
  ```bash
  npm run format
  ```
- Verify Prettier code style without modifying files:
  ```bash
  npm run format:check
  ```

## How to Use in Another Project

You can use this system in another project using either of the following approaches:

### Approach A: Integrated as a Sub-Router in an Existing Express App

1. Copy the `src/` folder into your target project (e.g. into `src/modules/auth/`).
2. Install the necessary packages in your target project:
   ```bash
   npm install bcryptjs jsonwebtoken zod cookie-parser express-useragent nodemailer pg redis
   npm install -D @types/bcryptjs @types/jsonwebtoken @types/cookie-parser @types/express-useragent @types/nodemailer @types/pg
   ```
3. In your main application file (`app.ts` or `index.ts`), import the database initializer, middleware, and router:
   ```typescript
   import express from "express";
   import cookieParser from "cookie-parser";
   import useragent from "express-useragent";
   import authRouter from "./modules/auth/routes/auth.routes.ts";
   import { initDB } from "./modules/auth/index.ts";

   const app = express();

   app.use(express.json());
   app.use(cookieParser());
   app.use(useragent.express());

   // Auto-create users and sessions tables on startup
   await initDB();

   // Mount authentication router
   app.use("/api/auth", authRouter);
   ```
4. Protect any custom endpoint in your existing application using the `authentication` middleware:
   ```typescript
   import { authentication } from "./modules/auth/middlewares/auth.middleware.ts";

   app.get("/api/dashboard", authentication, (req, res) => {
       res.json({
           message: "Access granted",
           user: req.user,
       });
   });
   ```

### Approach B: Run as a Standalone Microservice

1. Clone or fork this repository into its own workspace or container.
2. Provide database credentials and run `npm run start`.
3. Configure your frontend applications or backend microservices to communicate with `http://<auth-host>:8000/api/auth`.

## API Reference

### Public Routes

| Method | Endpoint | Description | Request Body |
|---|---|---|---|
| `POST` | `/api/auth/signup` | Send registration OTP to email | `{"name": "...", "email": "...", "password": "..."}` |
| `POST` | `/api/auth/verify-otp` | Verify OTP, create account, and log in | `{"email": "...", "otp": "123456"}` |
| `POST` | `/api/auth/resend-otp` | Resend registration OTP (60s cooldown) | `{"email": "..."}` |
| `POST` | `/api/auth/login` | Log in and receive tokens and cookies | `{"email": "...", "password": "..."}` |
| `POST` | `/api/auth/refresh` | Explicit token refresh | Read from cookies (`refreshToken`, `csrfToken`) and header `x-csrf-token` |
| `POST` | `/api/auth/forgot-password` | Request password reset OTP | `{"email": "..."}` |
| `POST` | `/api/auth/reset-password` | Set new password using OTP | `{"email": "...", "otp": "123456", "newPassword": "..."}` |

### Protected Routes (Requires `authentication` middleware)

| Method | Endpoint | Description | Request Body / Parameters |
|---|---|---|---|
| `GET` | `/api/auth/me` | Get profile of logged-in user | None |
| `PATCH` | `/api/auth/me` | Update user name | `{"name": "New Name"}` |
| `POST` | `/api/auth/logout` | Revoke current session and clear cookies | None |
| `POST` | `/api/auth/logout-all` | Revoke all active sessions across all devices | None |
| `GET` | `/api/auth/sessions` | List active sessions (device, IP, last used) | None |
| `DELETE` | `/api/auth/sessions/:sessionId` | Revoke a specific remote session | URL parameter `sessionId` |
| `PATCH` | `/api/auth/change-password` | Update password | `{"oldPassword": "...", "newPassword": "..."}` |
| `DELETE` | `/api/auth/me` | Permanently delete user account | None |

## Security Specifications

- **Password Hashing**: Passwords are encrypted with bcryptjs using a salt round of 10.
- **Timing-Safe CSRF**: Double-submit CSRF comparisons use `crypto.timingSafeEqual` to avoid timing attacks.
- **Pre-Registration Sandbox**: Unverified account registrations live solely in Redis with TTL expiration.
- **Anti-Enumeration Responses**: Password reset requests always return a uniform 200 response to prevent user discovery.
- **Cascade Revocation**: Changing or resetting a password immediately invalidates all active sessions across all devices.
